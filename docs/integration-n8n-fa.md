# یکپارچه‌سازی بیرونی سامانه با n8n

این سند «چرا» و «چطور» یکپارچه‌سازی است؛ راهنمای عملی در
`integrations/n8n/README.md` است.

## ۱. مسئله

سامانهٔ منابع انسانی کار خودش را کامل انجام می‌دهد، ولی بسیاری از کارهای روزمرهٔ
کارگزینی بیرون از آن تمام می‌شود: پیامک به کارمند، ایمیل گزارش ماهانه، همگام‌سازی با
سامانهٔ حسابداری، برداشت کارکرد از دستگاه اثر انگشت و یادآوری مهلت‌های قانونی. اگر همهٔ
این‌ها داخل هستهٔ Go نوشته شوند، سه هزینه می‌سازند: هر تغییر متن پیام یک استقرار تازه
می‌خواهد، هر سامانهٔ بیرونی با یک سبک، کد ماژول را شلوغ می‌کند، و آزمون‌های هسته به
شبکه وابسته می‌شوند.

n8n این لایه را بیرون می‌برد: یک موتور جریانِ بصری که «رخداد آمد → چه چیزی بفرست».

## ۲. معماری

```
        درخواست کاربر
             │
             ▼
   ┌───────────────────┐   ثبت تراکنشی    ┌──────────────────────┐
   │ hrmsd (Go)        │ ───────────────▶ │ hr_platform          │
   │  دامنه + API      │                  │   .event_outbox      │
   └───────────────────┘                  └──────────┬───────────┘
             │ پاسخ ۲xx بی‌درنگ                     │ گردانندهٔ پس‌زمینه
             ▼                                      │ (HMAC + تلاش مجدد)
        کاربر                                     ▼
                                        ┌──────────────────────┐
                                        │ n8n :5678/webhook     │
                                        │ بازبینی امضا → شاخه   │
                                        └──────────┬───────────┘
                                                   ▼
                                     پیامک / ایمیل / بله / سامانهٔ بیرونی
                                                   │
                                      (در صورت نیاز) خواندن جزئیات از API
                                      با سرآیند X-HRMS-Integration-Origin
```

سه تصمیم کلیدی:

1. **outbox به‌جای ارسال مستقیم.** رخداد اول در پایگاه‌داده ثبت می‌شود، بعد فرستاده
   می‌شود. نتیجه: قطعی یا کندی n8n نه پاسخ کاربر را کند می‌کند و نه رخدادی را گم می‌کند.
2. **رخداد سبک، جزئیات از API.** بدنهٔ کامل رکورد در رخداد نمی‌آید؛ مصرف‌کننده با
   `subject` (مثل `EMP-011`) خودش جزئیات را می‌خواند. یک منبع حقیقت، بدون تکرار داده و
   بدون خطر کهنه‌شدن.
3. **ثبت در یک نقطه.** میان‌افزار HTTP تغییرهای موفق API را ثبت می‌کند
   (`platform/events/middleware.go`). اگر ثبت در هر ماژول تکرار می‌شد، هر ماژول تازه
   می‌توانست فراموش کند.

## ۳. چه چیزی رخداد می‌سازد و چه چیزی نه

| وضعیت | رخداد؟ | چرا |
|---|---|---|
| `POST/PATCH/PUT/DELETE` با پاسخ ۲xx زیر `/api/v1/...` | بله | تغییر واقعی در سامانه |
| `GET` و بقیهٔ روش‌های خواندن | نه | تغییر نکرده است |
| درخواست ناموفق (۴xx/۵xx) | نه | تغییری رخ نداده |
| `/api/v1/auth/...` | نه | نشست، رخداد کسب‌وکاری نیست |
| `/api/v1/events/...` | نه | جلوگیری از حلقهٔ صندوق با خودش |
| درخواستی با سرآیند `X-HRMS-Integration-Origin` | نه | جلوگیری از حلقهٔ n8n ↔ سرور |

نام‌گذاری: `<ماژول>.<کنش>` — `employee.created`، `payroll.action`، `contracts.updated`.
مصرف‌کننده می‌تواند روی نام سوئیچ کند یا با `path` دقیق‌تر تصمیم بگیرد.

## ۴. قواعدی که نباید شکسته شوند

1. **هیچ قاعدهٔ کسب‌وکاری در n8n نیست.** جدول ۳۴۰۰۶، آیین‌نامهٔ صندوق نفت، ضرایب و
   سقف‌ها فقط در `server/internal/rules` (و مرجع Rust در `core/`) هستند. اگر فرمولی در
   n8n نوشته شود، دو منبع حقیقت ساخته می‌شود و بازتولیدپذیری فیش‌های گذشته از دست می‌رود.
2. **تصمیم تأیید در سرور می‌ماند.** n8n می‌تواند پیام بفرستد و لینک عمیق به کارتابل بدهد،
   ولی نباید با حساب سرویس دکمهٔ تأیید را بزند: در `audit` نام سرویس ثبت می‌شود نه انسان و
   ممیزی بی‌اعتبار می‌شود.
3. **کمترین دسترسی.** توکن سرویس n8n باید از حسابی با کمترین نقش گرفته شود؛ نه مدیر
   سیستم. مسیرهای `/api/v1/events/*` فقط برای مدیر است و به آن نیاز ندارد.
4. **کلید در مخزن نیست.** `HRMS_WEBHOOK_SECRET` به‌صورت HMAC روی `timestamp.body` امضا
   می‌شود؛ مُهر زمانی قدیمی‌تر از ۵ دقیقه در سمت n8n رد می‌شود (ضدِ بازپخش). کلیدها در
   `server/.env` و `integrations/n8n/.env` می‌مانند و هر دو در `.gitignore` هستند.
5. **پشتیبان‌گیری.** دادهٔ n8n (جریان‌ها، رمزهای ذخیره‌شده) در
   `%LOCALAPPDATA%\tools\n8n-data` است و با `encryption.key` همان پوشه رمز می‌شود؛ هر دو
   باید در بستهٔ پشتیبان نسخه (بخش ۵ `AGENTS.md`) باشند، وگرنه پس از بازگردانی، رمزهای
   ذخیره‌شده ناخوانا می‌شوند.

## ۵. آنچه n8n «بهینه» نمی‌کند

n8n کارایی سرور یا پایگاه‌داده را بهتر نمی‌کند و یک سرویس Node دیگر هم روی ماشین اضافه
می‌کند. ارزشش در **حذف کار دستی و کاهش خطای انسانی** است: گزارش‌هایی که کسی دستی
می‌ساخت، یادآوری‌هایی که فراموش می‌شد، ورود دوبارهٔ داده از سامانهٔ دیگر.

اگر هدف «سرعت و بار» است، مسیر درست ایندکس‌های Postgres، پروفایل کوئری‌های سنگین
(`hr_records.record` با جستجوی `fields::text`)، صفحه‌بندی و کش است — نه این لایه.

## ۶. سه سناریوی نخست پیشنهادی

| سناریو | محرک | کار جریان |
|---|---|---|
| یادآوری قرارداد نزدیک انقضا | زمان‌بند روزانه | `GET /api/v1/employee/employees` → فیلتر تاریخ → پیامک به کارگزینی |
| اطلاع تغییر پرونده | رخداد `employee.updated` | خواندن پرونده → پیامک/ایمیل به مدیر مستقیم |
| گزارش ماهانهٔ خودکار | زمان‌بند ماهانه | `GET /api/v1/statistics/dashboard` → فایل اکسل → ایمیل |

## ۷. آزمون و پایش

- آزمون واحد بستهٔ رویداد: `cd server && go test ./internal/platform/events/` — امضا،
  میان‌افزار (چه چیزی رخداد می‌شود و چه چیزی نه)، تحویل، تلاش مجدد و ناموفق‌ماندگار.
- آزمون انتها‌به‌انتها (اجراشده روی این ماشین، n8n 2.35.7 + Node 22.23.5): ویرایش پروندهٔ
  یک کارمند → رخداد `employee.updated` در صندوق → ارسال امضاشده به n8n → بازبینی امضا →
  ورود سرویس → خواندن پرونده از API → رسیدن نام و واحد کارمند به نود پایانی. اجرای
  گردش‌کار «success» و بدنهٔ رسیده شامل «امیر قاسمی / فناوری اطلاعات».
- آزمون منفی: درخواست با امضای جعلی، پاسخ ۲۰۰ می‌گیرد (وبهوک بی‌درنگ پاسخ می‌دهد) ولی
  اجرای گردش‌کار **error** می‌شود و هیچ پیامی به مقصد بعدی نمی‌رسد. یعنی امضا واقعاً
  جلوی رخداد جعلی را می‌گیرد.
- پایش: `GET /api/v1/events/config` شمار `pending/delivered/failed` را می‌دهد؛
  `GET /api/v1/events/outbox?status=failed` ردیف‌های مشکل‌دار، و
  `POST /api/v1/events/outbox/{id}/retry` بازگرداندن به صف.
- اگر صف `failed` بالا رفت، یعنی مقصد در دسترس نیست؛ رخدادها از دست نرفته‌اند.

## ۸. نکته‌های استقرار n8n (نسخهٔ ۲)

- دسترسی نود Code به `$env` پیش‌فرض بسته است؛ `tools\n8n\n8n.ps1` آن را با
  `N8N_BLOCK_ENV_ACCESS_IN_NODE=false` باز می‌کند و `crypto` را هم آزاد می‌کند. شنود فقط
  روی `127.0.0.1` است.
- فعال‌سازی گردش‌کار: `n8n publish:workflow --id=...` (دستور قدیمی `update:workflow --all`
  در نسخهٔ ۲ منسوخ شده).
- `N8N_ENCRYPTION_KEY` باید در فرمان‌های CLI هم همان کلید فایل `encryption.key` باشد؛
  وگرنه n8n با «Mismatching encryption keys» بالا نمی‌آید.
- توکن دسترسی ۳۰ دقیقه اعتبار دارد؛ به همین دلیل گردش‌کار «ورود سرویس» دارد و توکن ثابت
  ذخیره نمی‌کند. اگر حساب سرویس طولانی‌عمر لازم شد، باید در سرور «کلید سرویس» طراحی شود
  (کار جداگانه‌ای است و الان انجام نشده).
