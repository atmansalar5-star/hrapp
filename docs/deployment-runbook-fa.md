## ۰. خلاصهٔ صادقانه: امروز در چه وضعی هستیم

سه واقعیتی که پیش از هر تصمیمی باید بدانید:

1. **اجرای پیش‌فرض، دموی درون‌حافظه‌ای است.** سرور وقتی نشانی پایگاه‌داده تنظیم نشده
   باشد همه‌چیز را در حافظه می‌سازد و با هر بار خاموش/روشن شدن، داده به «دادهٔ نمونهٔ
   سازمانی» برمی‌گردد (`server/internal/bootstrap/bootstrap.go`).
2. **ذخیره‌سازی واقعی فقط برای بخشی از سامانه نوشته شده است.** حتی با Postgres،
   ماژول کارکنان و لایهٔ سکو (کاربران، سطوح دسترسی، زنجیرهٔ حسابرسی، لاگ سینک) هنوز
   انبار حافظه‌ای دارند و در هر راه‌اندازی از نو ساخته می‌شوند. اگر می‌خواهید این
   سامانه **دفتر ثبت رسمی** سازمان شود، این شکاف باید بسته شود (بخش ۵).
3. **مخزن هیچ کامیتی ندارد.** `git rev-parse HEAD` خطا می‌دهد و همهٔ فایل‌ها untracked
   هستند. یعنی امروز تنها سازوکار نگه‌داشت کار، **کپی پوشه** است — و همین باعث می‌شود
   پاسخ پرسش بک‌آپ (بخش ۴) مهم باشد.

جمع‌بندی: برای **نمایش، آموزش و اعتبارسنجی ضوابط با کاربران کلیدی** سامانه امروز
کامل قابل اجراست. برای **بهره‌برداری واقعی و ثبت دادهٔ پرسنلی** باید گام‌های ۳ تا ۵
(پایگاه‌داده، شکاف ذخیره‌سازی، امنیت حساب‌ها) انجام شود.

## ۱. نیازمندی‌ها

### ۱-۱. نرم‌افزار لازم روی ماشین اجرا

| نیاز | نسخه | برای چه | وضعیت روی این لپ‌تاپ |
|---|---|---|---|
| **Go** | ۱.۲۵ به بالا (سورس) — باینری ساخته‌شده به Go نیاز ندارد | ساخت `hrmsd` | ✅ ۱.۲۷.۱ در `~/tools/go` |
| **Node.js** | ۲۰ به بالا | فقط بازتولید خروجی‌ها و دروازه‌ها؛ برای اجرای سرور لازم نیست | ✅ ۲۶ |
| **Infisical CLI** | جدید | تزریق رمزها در زمان اجرا (رمز روی دیسک نمی‌ماند) | باید نصب و لاگین باشد |
| **PostgreSQL** | ۱۴ به بالا | ذخیره‌سازی واقعی (اختیاری در دمو، الزامی در بهره‌برداری) | نصب نیست |
| Java/Rust/Android SDK | — | فقط اگر اپ موبایل باید روی این ماشین ساخته شود | نصب نیست |

نکتهٔ وابستگی: سرور **تنها یک وابستگی بیرونی** دارد، `github.com/lib/pq` (درایور
Postgres) در `server/go.mod`. پس بیلد نخست به دسترسی شبکه یا `go mod download` نیاز
دارد؛ بعد از آن آفلاین هم بیلد می‌شود.

### ۱-۲. رمزها و پیکربندی (بدون این‌ها سرویس بالا می‌آید ولی قابل اتکا نیست)

رمزها روی دیسک نگه‌داری نمی‌شوند؛ در Infisical ثبت و در زمان اجرا تزریق می‌شوند:

| کلید | نقش | اگر نباشد |
|---|---|---|
| `HRMS_JWT_SECRET` | کلید امضای توکن ورود (HS256) | سرور یک کلید **موقت تصادفی** می‌سازد؛ با هر ری‌استارت همهٔ کاربران خارج می‌شوند |
| `HRMS_DATABASE_URL` | نشانی Postgres | اجرای درون‌حافظه‌ای (داده با ری‌استارت می‌رود) |
| `HRMS_MODULES` | فهرست ماژول‌های فعال با کاما | خالی = از پروفایل شرکت فعال |

نکتهٔ مهم دربارهٔ Infisical: فایل `server/.infisical.json` (پیوند پروژه) **همین حالا
وجود ندارد**؛ `start-HRMS.bat` به آن تکیه می‌کند. پس روی ماشین اجرا باید
`infisical login` و در پوشهٔ `server/` دستور `infisical init` اجرا شده باشد. اگر
می‌خواهید رمزها اصلاً از Infisical نیایند، جایگزین ساده‌تر این است که متغیرهای محیطی را
مستقیم در سرویس (NSSM/systemd) تنظیم کنید و `infisical run` را از فرمان حذف کنید.

### ۱-۳. داده و سند سازمانی

بدون دادهٔ واقعی، سامانه فقط «اسکلت واقعی با دادهٔ نمونه» است. فهرست دقیق اسناد و
جدولی که از شما لازم است در بخش ۳ سند [operations-plan-fa.md](operations-plan-fa.md)
آمده است (جداول حقوق، قالب قراردادها، چارت سازمانی، فهرست کارکنان، آیین‌نامه‌ها،
ماتریس تأیید).

### ۱-۴. زیرساخت پیشنهادی برای بهره‌برداری

- یک سرور ویندوز یا لینوکس با دست‌کم ۲ هسته و ۴ گیگ رم (بار واقعی این سامانه سبک است).
- PostgreSQL روی همان ماشین یا یک ماشین جدا با پشتیبان‌گیری خودکار.
- یک پروکسی معکوس (IIS/nginx/Caddy) برای TLS و دامنهٔ داخلی.
- دسترسی به شبکهٔ داخلی؛ این سامانه ذاتاً داخلی است و نباید بدون TLS روی اینترنت باز شود.

## ۲. نقشهٔ ذخیره‌سازی — چه چیزی می‌ماند و چه چیزی نمی‌ماند

این جدول ستون فقرات تصمیم‌های عملیاتی است. «Postgres» یعنی با تنظیم `HRMS_DATABASE_URL`
روی پایگاه‌داده نوشته می‌شود.

| داده | بدون `HRMS_DATABASE_URL` | با `HRMS_DATABASE_URL` |
|---|---|---|
| ۲۵ ماژول روی موتور مشترک (`bonus`، `cards`، `loans_retirement`، `welfare`، `education_bonus`، `attendance`، `payroll`، `training`، `discipline`، …) | حافظه + دادهٔ نمونه | **Postgres** (schema `hr_records`) |
| کارگزینی و قراردادها، احکام حقوق، خدمات پرسنلی | حافظه + دادهٔ نمونه | **Postgres** (schema اختصاصی هر ماژول) |
| **ماژول کارکنان** | حافظه + الگوی نمونه | **حافظه** ← حتی با Postgres هم نوشته نمی‌شود |
| کاربران و رمزها (`auth.SeedAccounts`) | حافظه | **حافظه** |
| سطوح دسترسی افزودهٔ مدیر | حافظه | **حافظه** |
| زنجیرهٔ حسابرسی | حافظه | **حافظه** |
| لاگ همگام‌سازی موبایل | حافظه | **حافظه** |

پیامد عملی: اگر امروز Postgres را هم وصل کنید، **فهرست کارکنان و حساب‌های کاربری در هر
راه‌اندازی از نو ساخته می‌شوند**، در حالی که پرداخت پاداش و قراردادها می‌مانند. این
ناهم‌خوانی در بهره‌برداری واقعی مشکل‌ساز است و به همین دلیل شکاف بخش ۵ در اولویت است.

> چرا مهاجرت `server/internal/modules/employee/migrations/0001_employee.sql` وجود دارد
> ولی اثری ندارد: فایل SQL آماده است، اما آداپتور Postgres ماژول کارکنان نوشته نشده و
> `employee/module.go` همیشه `infra.NewSeededStore()` می‌سازد.

## ۳. مراحل انجام کار

### گام ۰ — سه تصمیم پیش از شروع

1. **این سامانه دفتر ثبت رسمی می‌شود یا ابزار کمکی؟** اگر رسمی است، گام ۵ الزامی است.
2. **کدام شرکت فعال باشد؟** با `-org` یا `HRMS_ORG` (فهرست در `contracts/organizations.json`).
3. **قرارداد نسخه‌بندی**: امروز هیچ کامیتی وجود ندارد. پیش از هر تغییر واقعی، مخزن را
   نسخه‌بندی کنید (گام ۸-۳) تا «کپی پوشه» تنها سازوکار بازیابی نباشد.

### گام ۱ — آماده‌سازی ماشین

```bash
# Go (بدون دسترسی مدیر، همان روش این ماشین)
mkdir -p "$HOME/tools" && cd "$HOME/tools"
curl -sL -o go.zip https://go.dev/dl/go1.27.1.windows-amd64.zip && unzip -q -o go.zip
export PATH="$HOME/tools/go/bin:$PATH"

# Node (فقط برای بازتولید و دروازه‌ها)
node --version    # باید ≥ ۲۰ باشد

# Infisical (اگر مسیر تزریق رمز از Infisical باشد)
# نصب از مستندات رسمی، سپس:
infisical login
```

### گام ۲ — ساخت و بازبینی یکپارچگی

```bash
cd <ریشهٔ پروژه>

# ۱) دروازه‌ها: می‌سنجد خروجی‌های تولیدشده با مانیفست‌ها هم‌خوان‌اند
node tools/gen/gen.mjs --check
node tools/check/verify.mjs

# ۲) آزمون‌های سرور
cd server && go test ./...
```

اگر این دو دروازه سبز نشدند، **استقرار را ادامه ندهید**؛ یعنی نسخه‌ای که در دست دارید
با منابع خودش هم‌خوان نیست.

```bash
# ۳) ساخت باینری استقرار
cd server
go build -o bin/hrmsd.exe ./cmd/hrmsd
```

### گام ۳ — پایگاه‌داده و مهاجرت‌ها

```bash
# ساخت پایگاه‌داده و کاربر (یک‌بار)
createdb hrms       # یا از طریق pgAdmin/psql
```

نشانی را در محیط اجرا قرار دهید (نه در کد):

```bash
export HRMS_DATABASE_URL="postgres://hrms:<رمز>@127.0.0.1:5432/hrms?sslmode=disable"
```

مهاجرت‌ها **خودکار** در زمان راه‌اندازی اعمال می‌شوند (`-migrate` پیش‌فرض `true`) و
شامل این‌ها هستند: `server/migrations/0001_schemas.sql` (ساخت schemaها)،
`000_seed_rbac.sql` (تولیدشده از مانیفست‌ها) و `002_workflow_records.sql` (جدول موتور
رکورد)، به‌همراه `migrations/` هر ماژول. ترتیب، الفبایی روی نام فایل است.

برای اجرای دستی یا بازبینی:

```bash
cd server && ./bin/hrmsd.exe -db "$HRMS_DATABASE_URL" -migrate -root . -debug
```

بعد از بالا آمدن، آمادگی را بسنجید:

```bash
curl -s http://127.0.0.1:8080/readyz
# با Postgres: {"status":"ok","database":"connected","migrationsApplied":N,...}
# بدون Postgres: {"database":"in-memory",...}
```

### گام ۴ — اجرای دائمی به‌عنوان سرویس

`start-HRMS.bat` یک **راه‌انداز توسعه** است: پنجره باز می‌کند و با بستن پنجره سرور
خاموش می‌شود. برای اجرای دائمی، سرویس بسازید:

**ویندوز — با NSSM:**

```bat
nssm install HRMS "C:\hrms\server\bin\hrmsd.exe" ^
  -addr 127.0.0.1:8080 -web "C:\hrms\design\prototype" -root "C:\hrms\server"
nssm set HRMS AppDirectory "C:\hrms\server"
nssm set HRMS AppEnvironmentExtra HRMS_JWT_SECRET=... HRMS_DATABASE_URL=...
nssm set HRMS Start SERVICE_AUTO_START
nssm start HRMS
```

**لینوکس — با systemd:**

```ini
[Unit]
Description=HRMS
After=network.target postgresql.service

[Service]
WorkingDirectory=/opt/hrms/server
ExecStart=/opt/hrms/server/bin/hrmsd -addr 127.0.0.1:8080 -web /opt/hrms/design/prototype -root /opt/hrms/server
EnvironmentFile=/etc/hrms.env
Restart=always
User=hrms

[Install]
WantedBy=multi-user.target
```

سه پرچم مسیر که در سرویس باید **مطلق** باشند: `-web` (پوشهٔ رابط وب)، `-root` (ریشهٔ
پوشهٔ سرور برای یافتن `migrations`)، و `-addr`.

### گام ۵ — حساب‌ها، رمز اولیه و امنیت

پیش از هر دسترسی کاربر واقعی:

1. **رمزهای نمونه را عوض کنید.** حساب‌های `admin` / `hr.manager` / `hr.spec` /
   `line.mgr` / `employee` با رمز `demo` از `auth.SeedAccounts()` می‌آیند. تا وقتی
   کاربران روی پایگاه‌داده نوشته نشوند، تغییر رمز در رابط هم پایدار نیست — این را
   باید به‌عنوان بخشی از کار گام ۵-۱ ببینید.
2. **`HRMS_JWT_SECRET` را تزریق کنید** (یک رشتهٔ تصادفی بلند). بدون آن، هر راه‌اندازی
   کلید تازه می‌سازد.
3. **TLS و پروکسی معکوس**: سرور را روی `127.0.0.1` نگه دارید و TLS را روی پروکسی ببندید.
4. **بک‌فایر**: `/api/...` را از بیرون شبکه نبندید.
5. **آرایش شبکه**: `-web` رابط را روی `/` سرو می‌کند؛ این برای اجرای محلی و شبکهٔ داخلی
   مطلوب است. برای اینترنت، فایل‌های ایستا را جداگانه سرو کنید و `-web` را خالی بگذارید.
6. **حسابرسی**: زنجیرهٔ حسابرسی **در حافظه** است و پس از ری‌استارت پاک می‌شود. اگر
   لازم است سابقهٔ «چه کسی چه کرد» بمانَد، به بخش ۵ نگاه کنید.

### گام ۶ — پایش و آمادگی

دو مسیر برای probe و پایش:

| مسیر | معنا |
|---|---|
| `GET /healthz` | سرور بالا است؛ شرکت فعال، تعداد ماژول و تعداد اداره‌ها را برمی‌گرداند |
| `GET /readyz` | آمادگی واقعی: پاسخ پایگاه‌داده، تعداد مهاجرت‌های اعمال‌شده، سالم بودن زنجیرهٔ حسابرسی. اگر ناسالم باشد کد ۵۰۳ می‌دهد |

پایش پیشنهادی: فراخوانی دوره‌ای `/readyz` و هشدار روی کد ۵۰۳ یا `status != "ok"`.

### گام ۷ — به‌روزرسانی نسخه

```bash
# ۱) دروازه‌ها سبز باشند
node tools/gen/gen.mjs --check && node tools/check/verify.mjs
# ۲) بیلد تازه در مسیر مجاور
cd server && go build -o bin/hrmsd.new.exe ./cmd/hrmsd
# ۳) جابه‌جایی در زمان کم‌باری، با پشتیبان تازه (گام ۸)
# ۴) بررسی /readyz و بازگشت به نسخهٔ قبل در صورت خطا
```

### گام ۸ — پشتیبان‌گیری و بازیابی

**۸-۱. پیش از فعال‌کردن Postgres: پشتیبان = پوشهٔ پروژه.**

```bash
node tools/gen/gen.mjs --check > reports/backup-gen-$(date +%F).txt 2>&1
cd <پدرِ ریشهٔ پروژه>
tar --exclude='node_modules' --exclude='core/target' --exclude='server/bin' \
    -czf hrms-$(date +%F-%H%M).tar.gz <اسم پوشهٔ پروژه>
```

**۸-۲. با Postgres: پوشه کافی نیست، پایگاه‌داده هم لازم است.**

```bash
pg_dump --format=custom --file=hrms-db-$(date +%F).dump "$HRMS_DATABASE_URL"
# بازیابی:
pg_restore --clean --if-exists --dbname="$HRMS_DATABASE_URL" hrms-db-<تاریخ>.dump
```

**۸-۳. نسخه‌بندی کد (توصیهٔ جدی):** امروز هیچ تاریخی از تغییرات وجود ندارد. با یک
کامیت اولیه، از «کپی پوشه» به «تاریخ تغییرات + امکان بازگشت» می‌رسید. این کار
قواعد پروژه را نقض نمی‌کند چون کامیت فقط با درخواست صریح شما انجام می‌شود.

**۸-۴. آزمون بازیابی:** پشتیبانی که بازیابی نشده باشد، پشتیبان نیست. پس از هر بازیابی،
همان دو دروازه را اجرا کنید:

```bash
node tools/gen/gen.mjs --check && node tools/check/verify.mjs
```

## ۴. پاسخ مستقیم: «کپی پوشه به‌تنهایی برای بک‌آپ کافیست؟»

**برای کد و پیکربندی امروز: بله — و در واقع همین حالا تنها راه هم همین است**، چون مخزن
هیچ کامیتی ندارد و تاریخچه‌ای وجود ندارد که بتوان روی آن تکیه کرد.

**برای داده: نه.** هیچ دادهٔ پایگاه‌داده‌ای داخل پوشه نیست؛ اگر Postgres را وصل کنید،
داده جای دیگری است و بدون `pg_dump` از دست می‌رود.

نکته‌های ریزی که «کپی پوشه» را ناکافی یا پرخطر می‌کند:

| مورد | توضیح |
|---|---|
| **فایل‌های پنهان** | اگر کپی ابزارتان فایل‌های نقطه‌دار را نبرد، `server/.env`، `.gitignore`، `.github/` و `.freebuff/` از دست می‌روند. از `tar`/`robocopy` با تنظیم درست استفاده کنید. |
| **`server/.env`** | فایل استثناشده در `.gitignore` است و همین حالا یک `HRMS_JWT_SECRET` ۶۴ نویسه‌ای واقعی داخلش هست. یعنی **پشتیبان شما رمز دارد**؛ آن را مثل سند محرمانه نگه دارید و در اشتراک‌گذاری عمومی نگذارید. نکتهٔ دوم: اگر روزی پشتیبان را به گیت بسپارید، این فایل کامیت نمی‌شود و کلید از آن مسیر بیرون می‌ماند — پس پشتیبان پوشه را کنارش نگه دارید. |
| **`server/.infisical.json`** | همین حالا وجود ندارد. یعنی روی ماشین بازیابی‌شده باید `infisical login` + `infisical init` را دوباره انجام دهید، وگرنه `infisical run` نمی‌داند رمزها را از کدام پروژه بگیرد. |
| **حجم و آشغال** | پوشه‌های `node_modules`، `core/target` و `server/bin` بزرگ و بازتولیدشدنی‌اند؛ از بک‌آپ کنار بگذارید (با دستور ۸-۱). |
| **اسرار در Infisical** | رمزهای واقعی **در پوشه نیستند** (همین ویژگی امنیتی آن است). پشتیبان پوشه هرگز جای پشتیبان رمزها را نمی‌گیرد؛ دسترسی به پروژهٔ Infisical باید جداگانه تضمین شود. |
| **خروجی ساخت** | `server/bin/*.exe` باینری است، نه منبع. در بازیابی از نو بیلد کنید تا با کد همان نسخه هم‌خوان باشد. |
| **بی‌اعتباری خاموش** | اگر کپی ناقص باشد، هیچ خطایی نمی‌بینید تا زمانی که دیر شده باشد. برای همین **دروازه‌ها آزمون یکپارچگی بک‌آپ‌اند**: `gen --check` ثابت می‌کند خروجی‌های تولیدشده با مانیفست‌ها می‌خوانند و `verify.mjs` مرز معماری و رجیستری را می‌سنجد. |

**فهرست کوتاه پشتیبان درست در وضع کنونی:**

1. پوشهٔ پروژه، بدون `node_modules`/`core/target`/`server/bin`.
2. خروجی `node tools/gen/gen.mjs --check` و `node tools/check/verify.mjs` در کنار آن،
   به‌عنوان «سند سلامت» همان نسخه.
3. یادداشتی با تاریخ، شرکت فعال (`-org`)، و اینکه Postgres در کار بوده یا نه.
4. رمزها: از مسیر جدا (Infisical یا گاوصندوق رمز). هرگز فقط داخل پوشه.
5. پس از فعال‌شدن Postgres: فایل `pg_dump` همراه همان نسخه.

## ۵. شکاف‌هایی که پیش از «بهره‌برداری واقعی» باید بسته شود

به ترتیب اولویت:

1. **آداپتور Postgres برای ماژول کارکنان.** امروز فهرست کارکنان با هر راه‌اندازی از نو
   ساخته می‌شود، در حالی که پاداش و قراردادِ همان کارکنان روی Postgres می‌مانَد. تا
   رفع این، «شناسهٔ کارمند» مرجع پایدار ندارد. فایل مهاجرت
   (`employee/migrations/0001_employee.sql`) هست؛ اتصال انبار لازم است.
2. **کاربران، سطوح دسترسی، حسابرسی و لاگ سینک روی پایگاه‌داده.** بدون این، رمزها و
   سابقهٔ حسابرسی در هر ری‌استارت از دست می‌رود و مدیریت کاربر واقعی معنا ندارد.
3. **رمز اولیه و مدیریت رمز کاربران.** حساب‌های نمونهٔ `demo` باید در استقرار واقعی
   حذف یا اجبار به تغییر رمز شوند.
4. **پشتیبان‌گیری خودکار پایگاه‌داده** (زمان‌بندی‌شده) و **آزمون بازیابی دوره‌ای**.
5. **نسخه‌بندی مخزن** (کامیت اولیه) تا تغییرات قابل ردیابی و بازگشت‌پذیر شوند.
6. **اپ موبایل** (اختیاری): نیازمند نصب Rust و Android SDK و ساخت هستهٔ بومی.

## ۷. پیوست — فرمان‌های مرجع

```bash
# اجرای محلی (دموی درون‌حافظه‌ای) — رابط و API روی یک مبدأ
cd server && go run ./cmd/hrmsd -addr 127.0.0.1:8080 -web ../design/prototype

# همان سامانه برای شرکت دیگر
cd server && go run ./cmd/hrmsd -addr 127.0.0.1:8090 -org contractor_services -web ../design/prototype

# با پایگاه‌داده
cd server && ./bin/hrmsd.exe -addr 127.0.0.1:8080 -web ../design/prototype \
  -root . -db "$HRMS_DATABASE_URL" -migrate

# با رمزهای Infisical (همان کاری که npm run server و start-HRMS.bat می‌کنند)
cd server && infisical run --env=dev -- ./bin/hrmsd.exe -addr 127.0.0.1:8080 -web ../design/prototype

# بررسی سلامت و آمادگی
curl -s http://127.0.0.1:8080/healthz
curl -s http://127.0.0.1:8080/readyz

# بک‌آپ
pg_dump --format=custom --file=hrms-db-$(date +%F).dump "$HRMS_DATABASE_URL"
```

| پرچم | پیش‌فرض | کار |
|---|---|---|
| `-addr` | `:8080` | نشانی شنود |
| `-web` | `../design/prototype` | پوشهٔ رابط وب روی `/` (خالی = فقط API) |
| `-root` | `.` | ریشهٔ سرور برای یافتن `migrations` |
| `-env` | `.env` | فایل متغیرهای محیطی (متغیر محیطی موجود بازنویسی نمی‌شود) |
| `-org` | پروفایل پیش‌فرض | شرکت فعال |
| `-modules` | از شرکت فعال | فهرست صریح ماژول‌ها؛ بر `-org` مقدم |
| `-db` | `HRMS_DATABASE_URL` | نشانی Postgres؛ خالی = درون‌حافظه‌ای |
| `-migrate` | `true` | اعمال مهاجرت‌های اعمال‌نشده در راه‌اندازی |
| `-debug` | `false` | لاگ تفصیلی |
