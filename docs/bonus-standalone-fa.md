# «سیستم پاداش» — پلن ساخت و راهنمای اجرا روی یک رایانه

> این سند دو کار می‌کند: **پلن** (چه چیزی، چرا، با چه مرزهایی ساخته شد) و **مراحل اجرا**
> (از ساخت فایل اجرایی تا ورود، پشتیبان‌گیری و بازیابی).
>
> این زیرسامانه، ماژول پاداش همین سامانه است، ولی در یک **اجرای تفکیکی** با کمترین
> نیازمندی روی یک رایانه: بدون پایگاه‌داده، بدون Docker، بدون Node، بدون اینترنت و
> بدون سرویس بیرونی. سامانهٔ جامع منابع انسانی دست‌نخورده سر جایش می‌ماند؛ این یک
> بستهٔ جدا برای واحدی است که فقط کار پاداش را انجام می‌دهد.

---

## ۱. چرا این کار، و چه چیزی *نیست*

**مسئله:** واحد پاداش برای ثبت و پرداخت پاداش به یک ابزار کوچک نیاز دارد که روی
رایانهٔ خودش بالا بیاید. بالا آوردن کل سامانهٔ منابع انسانی برای این کار، پایگاه‌داده،
تنظیم رمزها و نگه‌داشت سرور می‌خواهد — یعنی هزینهٔ نگه‌داری برای کاری که یک نفر انجام
می‌دهد.

**راه‌حل:** یک فایل اجرایی که همه‌چیز در آن است. کاربر آن را اجرا می‌کند، مرورگر باز
می‌شود، وارد می‌شود و کار می‌کند.

**این بسته چه چیزی نیست (صادقانه):**

| نیست | چرا |
|---|---|
| نسخهٔ دوم منطق پاداش | دامنه، قواعد و قالب رکورد **همان** ماژول `bonus` سامانهٔ جامع است؛ هیچ قاعده‌ای تکرار نشد. |
| جایگزین سامانهٔ جامع | فقط پاداش را دارد؛ چارت سازمانی، کارگزینی، حقوق و قرارداد در آن نیست. |
| سیستم چندکاربرهٔ شبکه‌ای | پیش‌فرض روی `127.0.0.1` گوش می‌دهد؛ یک رایانه، یک کاربرِ کارشناس پاداش. |
| دارای پایگاه‌داده | داده در پوشهٔ داده روی دیسک است (فایل JSON + CSV). |

## ۲. معماری اجرای مستقل

```
bonusd.exe                 یک فایل اجرایی؛ رابط وب و API هر دو در آن جاسازی شده‌اند
bonus-data/                پوشهٔ داده؛ پشتیبان‌گیری = کپی همین پوشه
├── records.json           رکوردهای پرداخت پاداش (گردش‌کار، رخدادها، شمارندهٔ شناسه)
├── users.json             کاربران و رمز درهم‌شده (bcrypt) — رمز متن ساده هیچ‌جا ذخیره نمی‌شود
├── staff.csv              فهرست کارکنان؛ قابل ویرایش با Excel، بدون راه‌اندازی دوباره خوانده می‌شود
└── secret.key             کلید امضای نشست؛ ثابت می‌ماند تا با هر راه‌اندازی، ورودها باطل نشوند
```

**چهار تصمیم معماری که کار را ساده می‌کند:**

1. **یک فایل، نه یک پوشهٔ نصب.** رابط وب با `//go:embed` داخل باینری می‌نشیند
   (`localstore/webui`). پس نسخهٔ رابط و نسخهٔ سرور هرگز از هم جدا نمی‌شوند و CORS و
   مجوز مرورگر تنظیم اضافه نمی‌خواهد.
2. **انبار فایل، روی همان موتور رکورد.** `recordkit.FileStore` فقط «ماندگاری» را اضافه
   می‌کند و روی `MemoryStore` سوار است؛ پس فیلتر، صفحه‌بندی و شناسه‌گذاری یک نسخهٔ دوم
   ندارند.
3. **همان مسیرهای پلتفرم.** ورود، نشست، `/healthz` و دامنهٔ دسترسی همان کد استقرار
   سازمانی است (`registerPlatformRoutes`)، نه یک نسخهٔ سبک‌شدهٔ جدا.
4. **مرز ماژول دست‌نخورده.** تنها ماژول فعال «پاداش» است. مسیرهای بقیهٔ ماژول‌ها ثبت
   نمی‌شوند و درخواست به آن‌ها **۴۰۴ JSON** می‌گیرد، نه صفحهٔ HTML.

**فهرست کارکنان از کجا می‌آید:** از `staff.csv`. ماژول «کارکنان» در این اجرا سوار
نمی‌شود؛ به‌جایش `localstore.StaffStore` پورت کارکنان (`contracts.EmployeeReader`) را
پیاده می‌کند. پس فرم تخصیص پاداش بدون هیچ کارگزینی کار می‌کند و کارشناس فقط یک فایل را
با Excel به‌روز می‌کند.

## ۴. اجرا — گام به گام

### ۴-۱. ساخت (یک بار)

با Go ۱.۲۵ یا بالاتر:

```bash
cd server
go build -o bin/bonusd ./cmd/bonusd
```

یا از ریشهٔ مخزن:

```bash
make bonusd
```

خروجی: `server/bin/bonusd`. چون `-o` نام را عیناً می‌سازد، در ویندوز هم همین نام
بدون پسوند ساخته می‌شود (از Git Bash با `./bin/bonusd` اجرا می‌شود)؛ اگر پسوند
dاشتن را ترجیح می‌دهید، `go build -o bin/bonusd.exe ./cmd/bonusd` بزنید.
**این فایل خودکفاست**: روی رایانهٔ مقصد نه Go لازم است، نه Node، نه پایگاه‌داده.
همین دستور در `make bonusd` هم آمده است (روی این ماشین `make` نصب نیست؛ دستور
مستقیم بالا معادل آن است).

> برای بردن روی رایانهٔ دیگری، همان سیستم‌عامل و معماری را هدف بگیرید:
> ```bash
> cd server && GOOS=windows GOARCH=amd64 go build -o bin/bonusd.exe ./cmd/bonusd   # ویندوز ۶۴بیتی
> cd server && GOOS=windows GOARCH=386   go build -o bin/bonusd-386.exe ./cmd/bonusd  # ویندوز ۳۲بیتی
> cd server && GOOS=linux   GOARCH=amd64 go build -o bin/bonusd     ./cmd/bonusd   # لینوکس ۶۴بیتی
> ```
> یا با دستور کوتاه `make bonusd` (۶۴بیتی) و `make bonusd-386` (۳۲بیتی).
> چون هیچ وابستگی CGO در کار نیست، فایل ساخته‌شده روی همان سیستم‌عامل اجرا می‌شود.

### ۴-۲. راه‌اندازی

```bash
cd server
./bin/bonusd            # پوشهٔ داده: server/bonus-data  ←  http://127.0.0.1:8099
```

یا با باز شدن خودکار مرورگر از ریشهٔ مخزن:

```bash
make run-bonusd
```

در لاگ راه‌اندازی، وضعیت واقعی روی دیسک چاپ می‌شود: مسیر داده، شمار کارکنان، شمار
رکوردها و کاربر مدیر. اگر فایل کاربران تازه ساخته شود، هشدار **«رمز پیش‌فرض را عوض
کنید»** هم می‌آید.

**پرچم‌ها:**

| پرچم | پیش‌فرض | کار |
|---|---|---|
| `-addr` | `127.0.0.1:8099` | نشانی شنود؛ پیش‌فرض فقط روی همان رایانه |
| `-data` | `bonus-data` | پوشهٔ داده (رکوردها، کاربران، کارکنان، کلید) |
| `-admin-user` | `admin` | نام کاربری مدیر |
| `-admin-password` | — | رمز مدیر؛ برای **بازنشانی رمز** همان را ست کنید (بدون ویرایش فایل) |
| `-open` | خاموش | باز کردن مرورگر پیش‌فرض پس از راه‌اندازی |
| `-debug` | خاموش | لاگ تفصیلی |
| `-org` | شرکت پیش‌فرض | شناسهٔ شرکت فعال (نام برند در رابط و اسناد) |
| `-jwt-secret` | کلید پوشهٔ داده | کلید امضای نشست؛ خالی یعنی کلید پایدار محلی |

### ۴-۳. ورود

مرورگر را روی نشانی نشان‌داده‌شده باز کنید. در اجرای نخست:

```
کاربر: admin
رمز:  6468
```

> **همین‌جا رمز را عوض کنید.** یا با `-admin-password "رمز تازه"` یک بار بالا بیاورید
> (روی دیسک ذخیره می‌شود و اجرای بعدی همان را می‌پذیرد)، یا `users.json` را ویرایش
> کنید — ولی در حالت دوم باید رمز را درهم‌شده بنویسید، پس راه پرچم ساده‌تر است.

### ۴-۴. استفادهٔ روزمره

1. **داشبورد:** پرداخت به تفکیک مدیریت، نفر، نوع، دوره و وضعیت.
2. **تخصیص پاداش:** نوع پاداش، مدیریت، مبلغ، تاریخ پرداخت، روش پرداخت و شمارهٔ مصوبه؛
   کارکنان را از فهرست انتخاب کنید (جستجو دارد) و **پیش‌نمایش** بگیرید. پیش‌نمایش
   چیزی ذخیره نمی‌کند؛ با «ثبت»، برای هر نفر یک رکورد **پیش‌نویس** ساخته می‌شود.
3. **گردش‌کار پرداخت:** پیش‌نویس → «تأیید پرداخت» → «ثبت پرداخت». ویرایش و حذف فقط در
   وضعیت پیش‌نویس مجاز است؛ پس از تأیید فقط مسیر گردش‌کار می‌ماند. این قاعده در
   **دامنه** است، نه در رابط.
4. **خروجی CSV:** برای تحویل به حسابداری یا اکسل.
5. **گزارش چاپی:** دکمهٔ «🖨 چاپ گزارش» در نوار بالا، فهرست پرداخت‌ها را در یک صفحهٔ
   چاپی A4 با سرصفحهٔ «سیستم پاداش»، تاریخ شمسی و جمع مبلغ آماده می‌کند؛ با همان
   دکمه روی کاغذ چاپ یا به PDF ذخیره می‌شود. گزارش از همان دادهٔ سروری ساخته می‌شود
   (هیچ عددی در UI بازمحاسبه نمی‌شود) و در پایان جای امضای «تأییدکننده» و
   «تاریخ و مهر» دارد. نام مالک برنامه عمداً **در گزارش‌های چاپی نمی‌آید**.

**بالای صفحه:** آرم سازمان پتروشیمی بندر امام (دارایی جاسازی‌شده در خود باینری،
`assets/brand/logo-pgpic.jpg`) و خط «مالکیت برنامه: مسعود وائقی» در سرصفحهٔ برنامه
و همچنین صفحهٔ ورود دیده می‌شوند.

### ۴-۵. دفتر کارکنان (`staff.csv`)

```csv
کد پرسنلی,نام و نام خانوادگی,واحد,سمت,وضعیت
EMP-001,سارا محمدی,معاونت پشتیبانی خدمات,کارشناس ارشد,فعال
```

* فایل را با **Excel** باز و ویرایش کنید (کدگذاری UTF-8 با BOM). دو ستون اختیاری هم
  شناسایی می‌شوند: `تاریخ استخدام` و `نوع استخدام` (شرکتی/پیمانکاری).
* **نیازی به راه‌اندازی دوباره نیست:** سامانه زمان تغییر فایل را می‌پاید و خودش دوباره
  می‌خواند.
* سطر بی‌نام یا کد تکراری نادیده گرفته می‌شود و در رابط **هشدار** نشان داده می‌شود؛
  یعنی یک اشتباه تایپی بی‌صدا داده را خراب نمی‌کند.

### ۴-۶. پشتیبان‌گیری و بازیابی

* **پشتیبان:** سامانه را ببندید و **کل پوشهٔ داده** را کپی کنید (چهار فایل بخش ۲).
* **بازیابی:** پوشه را سر جایش برگردانید و سامانه را بالا بیاورید.
* اگر `records.json` خراب شود، سامانه **بی‌صدا دادهٔ خالی بالا نمی‌آید**؛ با پیام
  روشن و نام فایل خطا می‌دهد تا پشتیبان را بازگردانید. پس اگر پیام خطا دیدید،
  `records.json` را از پشتیبان برگردانید (یا نامش را عوض کنید تا از صفر شروع شود).

## ۶. نگه‌داشت روی رایانهٔ واحد پاداش (ویندوز)

1. **کپی:** فایل اجرایی (`bonusd.exe` — اگر نام بدون پسوند ساخته شده، پیش از کپی
   به `bonusd.exe` تغییر نام دهید) و پوشهٔ `bonus-data` را در یک پوشهٔ ثابت بگذارید
   (مثلاً `D:\Bonus`). میان‌بر روی دسکتاپ بسازید با هدف:
   `D:\Bonus\bonusd.exe -data D:\Bonus\bonus-data -open`
2. **دسترسی شبکه‌ای (اختیاری):** اگر می‌خواهید از رایانهٔ دیگری هم باز شود،
   `-addr 0.0.0.0:8099` بدهید و در **فایروال ویندوز** اجازهٔ ورودی همان درگاه را
   بدهید. توجه: در این حالت دیگر فقط روی همان رایانه نیست؛ رمز پیش‌فرض را حتماً عوض
   کنید و از شبکهٔ مطمئن استفاده کنید (سامانه روی HTTP ساده است).
3. **پشتیبان زمان‌بندی‌شده:** یک کار زمان‌بند ویندوز بسازید که پوشهٔ `bonus-data` را
   روزانه به درایو دیگر کپی کند. کافی است.
4. **به‌روزرسانی نسخه:** `bonusd.exe` را جانشین کنید و سامانه را دوباره بالا بیاورید؛
   پوشهٔ داده دست‌نخورده می‌ماند. پیش از جانشینی، یک کپی از پوشهٔ داده بگیرید.

## ۷. بستهٔ انتقال به رایانهٔ دیگر (کاملاً بیرون از پوشهٔ سامانه)

برای بردن سامانه روی یک رایانهٔ دیگر، به یک پوشهٔ **مستقل از مخزن** نیاز است که
هیچ ارجاعی به مسیر سامانهٔ منابع انسانی نداشته باشد. ساختار آن:

```
BonusStandalone-1.0.0/
├── bonusd.exe      سامانه (سرور + رابط، هر دو در یک فایل ۱۱ مگابایتی)
├── start.cmd       اجراکنندهٔ ویندوز؛ دوبار کلیک
├── backup.cmd      پشتیبان‌گیری زمان‌دار از پوشهٔ داده
├── staff.csv       فهرست کارکنان؛ با Excel ویرایش می‌شود
└── README-FA.txt   راهنمای فارسی کاربر نهایی
```

### ۷-۱. ساخت بسته (روی ماشین توسعه)

```bash
cd server
export PATH="$HOME/tools/go/bin:$PATH"
GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -ldflags "-s -w" \
  -o "$HOME/Desktop/BonusStandalone-1.0.0/bonusd.exe" ./cmd/bonusd
```

سه نکتهٔ عمدی در این دستور:

* `CGO_ENABLED=0` و `GOOS=windows` — هیچ وابستگی بومی در کار نیست، پس فایل ساخته‌شده
  روی رایانهٔ مقصد فقط با کپی اجرا می‌شود (برای لینوکس همان بالا با `GOOS=linux`).
* `-trimpath` — مسیرهای داخلی ماشین توسعه در باینری نمی‌مانند (در آزمون، رشتهٔ
  «hrapp» صفر بار در فایل پیدا شد).
* `-ldflags "-s -w"` — حذف اطلاعات اشکال‌زدایی؛ حجم از ۱۶ به ۱۱ مگابایت می‌رسد.

سپس `start.cmd`، `backup.cmd` و `README-FA.txt` را کنارش بگذارید و با
`Compress-Archive` یک ZIP بسازید تا انتقال با فلش ساده شود.

### ۷-۲. یک قاعدهٔ مهم دربارهٔ فایل‌های `.cmd`

فایل‌های دسته‌ای (`start.cmd`/`backup.cmd`) **تنها ASCII** هستند. علت: `cmd.exe`
محتوای فایل `.cmd` را با کدپیج کنسول می‌خواند و متن غیر-ASCII (فارسی) می‌تواند شکسته
شود و نیمهٔ یک خط به‌عنوان فرمان اجرا شود — خطای عجیبی که در همین آزمون دیده شد
(`'rl+C' is not recognized`). پس تمام راهنمای فارسی در `README-FA.txt` است و در
ابتدای `.cmd` فقط `chcp 65001` می‌آید تا پیام‌های فارسی خودِ سامانه در کنسول درست
دیده شوند.

### ۷-۳. راه‌اندازی روی رایانهٔ مقصد

1. کل پوشه (یا محتوای ZIP) را در مسیری مثل `D:\Bonus` بگذارید — نه "Program Files"
   و نه مسیر با حروف فارسی، تا دسترسی نوشتن دردسر نداشته باشد.
2. اگر فهرست واقعی کارکنان را دارید، `staff.csv` را جانشین کنید.
3. روی `start.cmd` دوبار کلیک کنید. داده در `bonus-data` همان پوشه ساخته می‌شود، پس
   انتقال دوبارهٔ پوشه، داده را هم می‌برد.
4. رمز پیش‌فرض را عوض کنید (بند ۴-۳).

### ۷-۴. آن‌چه آزموده شد (نه فقط ساخته شد)

* باینری ساخته‌شده روی مسیر مستقل اجرا شد و **داده‌اش را در همان پوشه** ساخت.
* همان بسته به یک پوشهٔ بی‌ربط کپی و اجرا شد ← بدون هیچ ارجاعی به مخزن کار کرد
  (ورود، ۱۲ کارمند از CSV خودش، ۲۰ رکورد نمایشی، تخصیص ۲۰۱).
* `start.cmd` واقعاً اجرا شد (درگاه ۸۰۹۹، ساخت `bonus-data`).
* `backup.cmd` واقعاً اجرا شد و پوشهٔ زمان‌دار با چهار فایل داده ساخت.
* ZIP ساخته و سالم بودنش بررسی شد (۵ ورودی، با پوشهٔ ریشه).

## ۸. نسخهٔ دسکتاپ ویندوزی (پنجرهٔ بومی، پرتابل)

همان سامانه، ولی مثل یک برنامهٔ نصب‌شده: یک پنجرهٔ ویندوزی با آیکون مستقل در نوار
وظیفه، بدون کنسول و بدون نوار نشانی مرورگر. کاربر روی فایل اجرایی دوبار کلیک می‌کند،
پنجره باز می‌شود، کار می‌کند و می‌بندد.

```
BonusApp-1.0.0/
├── bonusapp.exe          برنامه (سرور + پنجرهٔ WebView2، هر دو در یک فایل، ۱۱ مگابایت)
├── bonus-data/           دادهٔ خودش — کنار همین فایل می‌نشیند
│   └── staff.csv         فهرست کارکنان (پیش از اجرای نخست جانشین کنید)
└── README-FA.txt         راهنمای فارسی کاربر نهایی
```

### ۸-۱. چهار تصمیم معماری

1. **سرور درون همان فرآیند** (in-process) و روی `127.0.0.1` گوش می‌دهد؛ پس پنجره و
   داده یک برنامهٔ واحدند و هیچ فرآیند پس‌زمینهٔ گم‌شده باقی نمی‌ماند.
2. **پنجره با WebView2** (`github.com/jchv/go-webview2`) — همان رابط HTML را نشان
   می‌دهد، پس هیچ صفحه‌ای بازنویسی نشد و «عیناً همان برنامه» است، نه یک کپی هم‌رفتار.
3. **بدون CGO و بدون DLL همراه**: موتور WebView2 داخل خود فایل اجرایی جاسازی شده
   است (`//go:embed` در بستهٔ WebView2) و هیچ `.syso` در کار نیست، پس همان تعهد
   «یک فایل، بدون پیش‌نیاز» حفظ می‌شود. تنها پیش‌نیاز، WebView2 Runtime است که روی
   ویندوز ۱۰/۱۱ از پیش نصب است.
4. **پل بومی برای کارهایی که وب نمی‌تواند**: دو دکمهٔ «📂 پوشهٔ داده» و
   «🗄 ساخت پشتیبان» فقط وقتی دیده می‌شوند که برنامه داخل پنجرهٔ بومی باشد
   (وجود توابع تزریق‌شده در جاوااسکریپت تشخیص داده می‌شود). پس یک فایل HTML برای
   هر دو نسخه کار می‌کند و هیچ قاعده‌ای در UI تکرار نشد.

### ۸-۲. ساخت و اجرا

```bash
make bonusapp        # ویندوز ۶۴بیتی → server/bin/bonusapp.exe
make bonusapp-386    # ویندوز ۳۲بیتی → server/bin/bonusapp-386.exe
make run-bonusapp    # اجرا روی همین ویندوز
```

معادل دستی (هر دو یکی است):

```bash
cd server && GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -trimpath \
  -ldflags "-s -w -H=windowsgui" -o bin/bonusapp.exe ./cmd/bonusapp
# ویندوز ۳۲بیتی (x86): همان دستور، فقط معماری عوض می‌شود
cd server && GOOS=windows GOARCH=386 CGO_ENABLED=0 go build -trimpath \
  -ldflags "-s -w -H=windowsgui" -o bin/bonusapp-386.exe ./cmd/bonusapp
```

**دربارهٔ نسخهٔ ۳۲بیتی:** همان کد است و تنها معماری عوض می‌شود؛ ساخت هنوز بدون CGO و
بدون DLL همراه است. موتور WebView2 باید هم‌معماری با خود برنامه باشد؛ روی ویندوزهایی
که WebView2 Runtime معمولی (همراه Edge) نصب است، معمولاً هر دو معماری در دسترس‌اند.
این ادعا فقط حرف نیست: نسخهٔ ۳۲بیتی روی همین ماشین آزموده شد و پنجرهٔ بومی واقعاً
رابط را رندر کرد (ردّ `shell-loaded` و ساخت پروفایل `webview2`). اگر روی سامانه‌ای
موتور WebView2 نبود، برنامه به‌جای خطای مبهم، آدرس مرورگر و مسیر داده را در یک پیام
بومی نشان می‌دهد؛ پس هیچ‌وقت کاربر بی‌راهنما نمی‌ماند.

`-H=windowsgui` یعنی زیرسیستم GUI: بدون پنجرهٔ سیاه کنسول. در عوض گزارش برنامه در
فایل `bonus-data/bonusapp.log` می‌نشیند و خطاهای کشنده در یک پیام بومی ویندوزی
(MessageBox) نشان داده می‌شوند تا بی‌صدا نمانند.

پرچم‌ها: `-data` (پوشهٔ داده)، `-port` (پیش‌فرض ۸۰۹۹ و در صورت اشغال، درگاه آزاد
با ثبت هشدار)، `-admin-user`، `-admin-password` (بازنشانی رمز)، `-debug`.

### ۸-۳. چیزهایی که فقط نسخهٔ دسکتاپ دارد

| ویژگی | چرا |
|---|---|
| دکمهٔ «پوشهٔ داده» | باز کردن پوشه در ویندوز، برای کپی دستی |
| دکمهٔ «ساخت پشتیبان» | کپی زمان‌دار از داده با گزارش شمار فایل‌ها |
| تک‌نسخه‌ای با میوتکس نام‌دار (Mutex) | دو نویسنده روی یک فایل داده، داده را خراب می‌کند؛ میوتکس با بسته شدن فرآیند خودکار آزاد می‌شود، پس «قفل مرده» نمی‌ماند |
| آگاهی از مقیاس نمایشگر (DPI) | متن روی نمایشگرهای ۱۲۵٪ و بالاتر تار نمی‌شود |
| گزارش «رابط بار شد» | در لاگ می‌نویسد کدام نسخه، چند کارمند و چند رکورد به کاربر نشان داده شد؛ برای پشتیبانی |
| پروفایل موتور داخل پوشهٔ داده | هر ردّ برنامه در یک پوشه می‌ماند؛ پشتیبان‌گیری و انتقال ساده است |

### ۸-۴. چه چیزی آزموده شد (نه فقط ساخته شد)

* **ساخت بدون CGO** روی ویندوز و همچنین ساخت شکل غیر-ویندوزی (تا دروازه‌های پروژه روی
  سیستم‌عامل‌های دیگر سبز بمانند).
* **زیرسیستم فایل اجرایی** با خواندن هدر PE بررسی شد: `Subsystem = 2` یعنی GUI و بدون
  کنسول.
* **پنجرهٔ بومی واقعاً رابط را رندر کرد**: خودِ صفحه با پل داخلی گزارش داد
  (`stage=shell-loaded` در ۳ ثانیه پس از اجرا) و پس از ورود کاربر، گزارش کامل
  (`stage=ui-ready` با عنوان، نوع رکورد، ۴ زبانه، ۶ نوع پاداش، ۱۲ کارمند و ۲۰ رکورد).
  یعنی ادعای «پنجره باز شد» با شاهدِ درون صفحه تأیید شد، نه با حدس.
* **کل ردّ برنامه در پوشهٔ خودش ساخته شد**: `records.json`، `users.json`،
  `staff.csv`، `secret.key`، `bonusapp.log` و پروفایل `webview2`.
* **دکمهٔ پشتیبان**: منطق کپی با ۵ آزمون دامنه‌ای آزموده شد (کپی کامل چهار فایل داده،
  نادیده‌گرفتن پروفایل مرورگر و پوشهٔ پشتیبان‌های پیشین، حفظ زیرپوشه‌ها، خطای صریح در
  پوشهٔ دادهٔ خالی/ناموجود/مقصد نامعتبر، و تکرارپذیری).
* **درگاه اشغال**: وقتی ۸۰۹۹ در دست برنامهٔ دیگری بود، برنامه درگاه آزاد گرفت و همان را
  در لاگ هشدار داد.

## ۹. محدودیت‌های آگاهانه

1. **حساب کاربری یکی است.** فایل کاربران می‌تواند چند کاربر داشته باشد و رمزها امن
   ذخیره می‌شوند، ولی رابط مدیریت کاربر در این بسته نیست؛ کاربر تازه یعنی یک ورودی در
   `users.json` (یا اجرای دوباره با `-admin-password`).
2. **حسابرسی و لاگ‌ها در حافظه‌اند.** رخدادهای هر رکورد (`events`) در فایل داده
   می‌مانند، ولی زنجیرهٔ حسابرسی سراسری و لاگ سینک استقرار سازمانی در این بسته
   ماندگار نمی‌شوند.
3. **تک‌رایانه‌ای است، نه چندنویسنده.** فایل داده برای یک کاربر طراحی شده؛ اجرای دو
   نمونه روی یک پوشهٔ داده پشتیبانی نمی‌شود.
4. **بدون HTTPS و بدون CORS باز.** پیش‌فرض روی `127.0.0.1` است. برای دسترسی از شبکه،
   پیش از آن یک پروکسی معکوس با TLS بگذارید.
5. **دادهٔ نمونه در اجرای نخست.** نمونهٔ پرداخت‌های پاداش برای آنکه کاربر رابط را خالی
   نبیند کاشته می‌شود. برای شروع با دادهٔ خالی، پس از نخستین اجرا رکوردها را از رابط
   حذف کنید (یا `records.json` را با یک فایل خالی جانشین کنید).
6. **نسخهٔ ۳۲بیتی اپ دسکتاپ به موتور WebView2 هم‌معماری نیاز دارد.** نسخهٔ ۳۲بیتی
   `bonusd` هیچ پیش‌نیازی ندارد. نسخهٔ ۳۲بیتی `bonusapp` هم روی همین ماشین (ویندوز
   ۶۴بیتی با WebView2 معمولی) پنجره را باز کرد؛ ولی اگر سامانه‌ای فقط موتور x64 داشته
   باشد، برنامه پنجره را باز نمی‌کند و به مسیر مرورگر می‌افتد. این محدودیت WebView2
   است، نه کد؛ راه‌حل: بستهٔ x86 «Microsoft Edge WebView2 Runtime» را نصب کنید یا از
   نسخهٔ ۶۴بیتی استفاده کنید.
7. **ویندوز ۷/۸/۸٫۱ پشتیبانی نمی‌شود.** هر دو نسخه برنامه‌های Go هستند و کد سامانه از
   امکانات Go 1.22 (`http.Request.PathValue`) و Go 1.24 (`crypto/pbkdf2`) استفاده
   می‌کند؛ Go از نسخهٔ ۱٫۲۱ به بعد رسماً فقط ویندوز ۱۰ و بالاتر را پشتیبانی می‌کند، پس
   باینری روی ویندوز ۸ اجرا نمی‌شود. افزون بر آن، آخرین نسخهٔ WebView2 برای ویندوز
   ۷/۸ همان ۱۰۹ است (ژانویهٔ ۲۰۲۳) و «WebView2 SDK از ۱٫۰٫۱۵۱۹٫۰ به بالا ویندوز ۷ و
   ۸/۸٫۱ را پشتیبانی نمی‌کند»؛ پس پنجرهٔ نسخهٔ دسکتاپ روی این ویندوزها هم ساخته
   نمی‌شود. راه‌حل بدون ارتقا: `bonusd.exe` را روی یک رایانهٔ ویندوز ۱۰/۱۱ با
   `-addr 0.0.0.0:8099` اجرا کنید (لاگ، نشانی شبکهٔ محلی را چاپ می‌کند)، در فایروال
   همان درگاه را باز کنید و از مرورگر رایانهٔ ویندوز ۸ به آن نشانی وصل شوید. راه پایدار
   هم ارتقای رایانه به ویندوز ۱۰/۱۱ است.
