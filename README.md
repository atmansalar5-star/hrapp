# سامانه جامع منابع انسانی — هستهٔ Rust، کلاینت React Native، سرور Go

سامانهٔ ماژولار منابع انسانی بر پایهٔ سند طراحی فارسی (`design/prompt.txt`): ۵ نقش،
**۲ حوزهٔ سازمانی، ۹ اداره، ۲۵ زیرواحد، ۲۶ ماژول و ۸۹ صفحه**، راست‌چین کامل و مستندات
صفحه‌به‌صفحهٔ فارسی.

منو به‌صورت «حوزهٔ سازمانی > ادارهٔ منابع انسانی > زیرواحد > ماژول > صفحه» سازمان یافته
است و همین درخت از یک منبع واحد (`contracts/departments.json` + مانیفست هر ماژول) برای
سرور Go، اپ React Native و نمونهٔ تحت وب تولید می‌شود.

همین یک سامانه برای **چند شرکت شبیه‌سازی می‌شود**: استقرار فعلی برای **پتروشیمی بندر امام**
از **هلدینگ خلیج فارس** بالا می‌آید و سه استقرار پارامتریک دیگر (ستاد هلدینگ، یک پتروشیمی
نمونه و یک شرکت پیمانکاری نمونه) در `contracts/organizations.json` تعریف شده‌اند؛ هر شرکت
ادارات و ماژول‌های فعال، پارامترهای حقوقی-مالی و مشخصات برند خود را دارد.

> این مخزن بر پایهٔ سه تصمیم معماری ساخته شده است:
> **هستهٔ کلاینت با Rust**، **رابط کاربری با React Native** و **سرور با Go به‌شکل
> مونولیت ماژولار با مرزهای اجبارشده**.

## معماری در یک نگاه

```
React Native ──(TurboModule / JSI)──►  hrms-ffi (تنها دروازهٔ هسته)
   │                                        ├─ hrms-domain    انواع و اعتبارسنجی
   │  فقط نمایش، ناوبری، i18n               ├─ hrms-calendar  تقویم شمسی و روز کاری
   │                                        ├─ hrms-rules     حقوق، مرخصی، عملکرد
   ▼                                        ├─ hrms-policy    RBAC (تولیدشده از مانیفست)
HTTPS/JSON ────────────────►  hrmsd (Go)    └─ hrms-store     انبار محلی، Outbox، سینک
                            مرجع نهایی
```

سه قاعده‌ای که همه‌چیز را نگه می‌دارد:

1. **هیچ قاعدهٔ کسب‌وکاری در UI نیست.** اعتبارسنجی، محاسبهٔ حقوق و مرخصی، تقویم و
   منوی نقش‌محور همه از هستهٔ بومی می‌آید. اگر هسته بار نشود، کلاینت محاسبه نمی‌کند و
   خطای صریح می‌دهد؛ نسخهٔ دومی از قواعد در جاوااسکریپت ساخته نمی‌شود.
2. **سرور مرجع نهایی است.** محدودهٔ دسترسی نقش (`all` / `own_unit` / `own`) در کوئری
   سرور اعمال می‌شود؛ پنهان‌کردن در کلاینت به‌تنهایی ارزش امنیتی ندارد.
3. **یک مانیفست، همهٔ مشتقات.** `server/internal/modules/*/module.json` منبع واحد است و
   از آن ساخته می‌شود: رجیستری Go، منوی React Native، جدول سیاست Rust، seed دسترسی‌ها،
   انواع TypeScript و مستندات فارسی. انحراف هر یک، CI را می‌شکند.
4. **استقرار پارامتریک از داده می‌آید، نه از کد.** فعال بودن ادارات و ماژول‌ها، پارامترهای
   حقوقی-مالی و مشخصات برند هر شرکت در `contracts/organizations.json` است؛ سرور، اپ و
   نمونهٔ تحت وب هر سه از همان فایل تولید می‌شوند، پس رفتارشان برای شرکت‌های دیگر یکی است.

شرح وظایف هر حوزه، اداره و زیرواحد در `contracts/departments.json` است و همان متن در
`docs/generated/pages-fa.md` و در راهنمای شناور (tooltip) سرگروه‌های منو دیده می‌شود.

دو نکتهٔ ساختاری:

- **زیرواحد** فقط یک برچسب گروه‌بندی در منو است؛ دسترسی و منطق ندارد و همه‌چیز مانند قبل
  روی مرز ماژول می‌ایستد. هر ماژول با کلید `subUnit` به زیرواحد خودش وصل می‌شود.
- **ماژول مشترک:** طبقه‌بندی مشاغل بین واحد امور کارکنان و واحد برون‌سپاری مشترک است؛
  یک ماژول و یک API است که با کلید `sharedWith` در منوی هر دو اداره دیده می‌شود (در
  نمونهٔ تحت وب با برچسب «مشترک»). یک بار کد، دو جای منو.

## استقرار پارامتریک برای چند شرکت

منبع واحد استقرارها `contracts/organizations.json` است و از آن تولید می‌شود:
پروفایل شرکت‌ها در Go (`server/internal/platform/orgs/orgs.gen.go`)، در اپ React Native
(`apps/mobile/src/config/organizations.generated.ts`) و در نمونهٔ تحت وب
(`design/prototype/js/organizations.generated.js`).

| شرکت | هلدینگ | کد | ادارهٔ فعال | ماژول فعال | کارکنان |
|---|---|---|---:|---:|---:|
| پتروشیمی بندر امام (استقرار مرجع) | هلدینگ خلیج فارس | `BIPC` | ۹ | ۲۶ | ۴٬۲۰۰ |
| ستاد هلدینگ خلیج فارس | هلدینگ خلیج فارس | `PGH` | ۵ | ۱۰ | ۳۲۰ |
| شرکت پتروشیمی نمونه | هلدینگ نمونه | `SPC` | ۷ | ۲۳ | ۸۵۰ |
| شرکت خدمات و پیمانکاری نمونه | هلدینگ نمونه | `CSC` | ۵ | ۱۴ | ۱٬۵۰۰ |

هر شرکت تعیین می‌کند: کدام اداره‌ها فعال باشند (`enabledDepartments`)، کدام ماژول‌ها
خاموش شوند (`disabledModules`)، پارامترهای حقوقی-مالی چه مقادیری داشته باشند
(`paramOverrides` روی `defaultParams`) و مشخصات برند/تقویم/سال مالی چیست.

در سرور Go این انتخاب با پرچم `-org` یا متغیر `HRMS_ORG` انجام می‌شود و اثر واقعی دارد:
ماژول‌های غیرفعال همان شرکت **ثبت نمی‌شوند** (مسیرشان وجود ندارد) و `/healthz` شرکت فعال
را گزارش می‌کند. در نمونهٔ تحت وب همین کار با انتخابگر شرکت در نوار بالا انجام می‌شود و
ماژول خاموش، از منو حذف و با مسیر دستی هم باز نمی‌شود.

## ساختار مخزن

```
core/          هستهٔ Rust (۷ crate) + fixtureهای طلایی قواعد
server/        سرور Go: cmd/hrmsd، platform/{orgs,modules,rbac,audit,…}، modules/<۲۶ ماژول>، migrations/
apps/mobile/   کلاینت React Native: core/، config/، navigation/، features/<۲۶ ماژول>/
contracts/     OpenAPI و JSON Schema + خروجی‌های تولیدشده (Go/TS/Rust)
tools/         تولیدکننده و دروازه‌های بررسی (بدون وابستگی خارجی)
design/        بستهٔ طراحی تأییدشده: پروتوتایپ، Wireframe، User Flow و مستندات فارسی
docs/          مستندات معماری، راه‌اندازی و مستندات فارسی تولیدشده هر صفحه
```

## شروع کار

```bash
# ۱) بازتولید خروجی‌ها از مانیفست‌ها و اجرای دروازه‌های بررسی
npm run gen
npm run verify

# ۲) سرور + رابط وب روی یک مبدأ واحد (نیازمند Go 1.24+)
cd server && go run ./cmd/hrmsd -addr 127.0.0.1:8080 -web ../design/prototype
# سپس در مرورگر: http://127.0.0.1:8080/

# همان سرور برای شرکت دیگری (استقرار پارامتریک): فقط پرچم -org عوض می‌شود
cd server && go run ./cmd/hrmsd -addr 127.0.0.1:8090 -org contractor_services -web ../design/prototype
curl -s http://127.0.0.1:8090/healthz   # تعداد ماژول‌های همان شرکت را گزارش می‌کند

# ۳) هسته و تطبیق قواعد (نیازمند Rust 1.75+)
cd core && cargo test --workspace --all-features
cargo run -p hrms-conformance

# ۴) کلاینت موبایل (نیازمند Node 20+ و JDK/Android SDK)
cd apps/mobile && npm install && npm start
```

با پرچم `-web` رابط روی `/` و API روی `/api/v1/...` همان مبدأ سرو می‌شود؛ پس در اجرای
محلی هیچ تنظیم CORS یا آدرس جداگانه‌ای لازم نیست و ورود در مرورگر روی توکن واقعی JWT
انجام می‌شود. «یک ماژول، همهٔ مشتقات»: همان درخت منو که مرورگر می‌بیند، از پاسخ
`GET /api/v1/auth/me` هم برمی‌گردد.

### اجرای سریع روی ویندوز (بدون تایپ دستور)

روی ریشهٔ پروژه فایل **`start-HRMS.bat`** هست؛ کافی است دوبار کلیک کنید:

1. بار اول سرور را می‌سازد (`server\bin\hrmsd.exe`) و از دفعهٔ بعد فوری بالا می‌آید.
2. سرور را روی `127.0.0.1:8080` اجرا و مرورگر را خودش باز می‌کند.
3. اگر Go روی `PATH` نباشد، خودش مسیر `%USERPROFILE%\tools\go\bin` را امتحان می‌کند.

> ⚠ **پنجرهٔ سیاه (کنسول) را نبندید** — سرور همان‌جا در حال اجراست و بستن پنجره
> یعنی خاموش شدن برنامه. برای توقف، `Ctrl+C` بزنید یا پنجره را ببندید.

نکته‌ها:

- آدرس برنامه `http://127.0.0.1:8080/` است. اگر `localhost` باز نکرد، همین آدرس
  عددی را بزنید (مرورگر گاهی `localhost` را روی IPv6 امتحان می‌کند).
- اگر سرور از قبل در حال اجراست، اسکریپت دوباره بالا نمی‌آورد و فقط مرورگر را باز می‌کند.
- بعد از تغییر کد، با `start-HRMS.bat rebuild` باینری را از نو بسازید.
- اگر پورت ۸۰۸۰ اشغال باشد، سرور خطا می‌دهد؛ اول پنجرهٔ سرور قبلی را ببندید.

سرور فقط تا وقتی پنجرهٔ خودش باز است کار می‌کند؛ پس اگر آن را از یک نشست موقت
(مثل ابزار دستیار) اجرا کنید، با بسته‌شدن آن نشست خاموش می‌شود. برای اجرای پایدار،
همیشه از همین فایل یا یک ترمینال خودتان استفاده کنید.

```bash
# آزمون‌های سرور (همه ماژول‌ها، حدود ۲۰ ثانیه)
cd server && go test ./...
```

> **وضعیت زنجیرهٔ ابزار:** Go 1.27.1 به‌صورت محلی برای همین کاربر نصب شده است
> (`~/tools/go`، بدون نیاز به دسترسی مدیر) و کل سرور **کامپایل می‌شود و همهٔ آزمون‌هایش
> سبز است**. Rust و JDK/Android SDK هنوز نصب نیستند، پس هستهٔ بومی و کلاینت موبایل روی
> این ماشین ساخته نمی‌شوند؛ گردش کار CI در `.github/workflows/ci.yml` آن‌ها را روی
> runnerهای استاندارد اجرا می‌کند. راهنمای نصب در `docs/setup-fa.md` است.

| `hr.spec` | کارشناس منابع انسانی | کل سازمان (بدون حذف) |
| `line.mgr` | مدیر واحد فناوری اطلاعات | واحد خودش |
| `employee` | کارمند (فاطمه صادقی) | فقط پروندهٔ خودش |

## دروازهٔ «یک قاعده، دو میزبان»

قواعدی که هم کلاینت و هم سرور باید ارزیابی کنند یک‌بار در `core/crates/hrms-rules`
نوشته می‌شوند و خروجی آن‌ها در `core/testdata/conformance/*.json` ثابت می‌گردد. سرور Go
همان فایل‌ها را می‌خواند و پیاده‌سازی خودش را می‌سنجد:

```bash
cd core   && cargo run -p hrms-conformance   # مرجع: تولید/بازبینی fixtureها
cd server && go test -run Parity ./internal/rules/...
```

اختلاف عددی در هر یک از این‌ها CI را می‌شکند.

## آزمون دودی روی Postgres

آزمون‌های دیگر همه روی انبار درون‌حافظه‌ای اجرا می‌شوند و ایرادهای «بذرکاری روی
پایگاه‌دادهٔ واقعی» را نمی‌بینند. آزمون دودی سرور واقعی را روی Postgres بالا می‌آورد و
سه چیز را می‌سنجد: **پُری همهٔ ماژول‌ها** (هر نوع رکورد دست‌کم یک رکورد)،
**چرخهٔ ایجاد/جستجو/ویرایش/حذف روی هر نوع رکورد**، و **اشتراک داده بین دو نمونهٔ سرور**
روی همان پایگاه‌داده (تا حافظه‌ای‌بودن انبار رد شود). در CI روی سرویس `postgres:17`
اجرا می‌شود:

```bash
# محلی: DSN یک پایگاه‌دادهٔ آزمایشی بدهید (نه پایگاه‌دادهٔ کار)
HRMS_TEST_DATABASE_URL="postgres://hrms@127.0.0.1:5432/hrms_smoke?sslmode=disable" make smoke-postgres
```

بدون آن متغیر، آزمون رد می‌شود و `go test ./...` به پایگاه‌دادهٔ توسعه‌ای کسی دست نمی‌زند.
دروازهٔ یکتایی پیشوند شناسهٔ انواع رکورد (`TestRecordKindIDPrefixesAreUniqueAcrossModules`)
بدون نیاز به پایگاه‌داده و در همان آزمون‌های همیشگی اجرا می‌شود.

## مرحلهٔ فعلی

فاز ۰ (پایه) و **برش عمودی فاز ۱** (ورود + RBAC + ماژول کارکنان) انجام شده است.
ساختار سازمانی کامل (۲۶ ماژول / ۸۹ صفحه) روی همین پایه سوار است.

**همهٔ ۲۶ ماژول روی دادهٔ واقعی سرور کار می‌کنند.** ماژول‌های اداری (انتصابات،
بایگانی، انضباط کار، حضور و غیاب، حقوق و دستمزد، رفاه، وام و بازنشستگی، آموزش، آمار،
مطالعات، برون‌سپاری، شکایات، مددکاری، درمان، جذب نیرو، عملکرد، طبقه‌بندی مشاغل،
جابه‌جایی، گزارش‌ها و تنظیمات) روی موتور مشترک **`recordkit`** سوار شده‌اند: قواعد هر
ماژول در بستهٔ `domain` خودش اعلام می‌شود (نوع رکورد، فیلدها، وضعیت‌ها، انتقال‌های مجاز
و اقدام‌ها) و سرور همان را اجرا می‌کند — اعتبارسنجی، گردش‌کار تأیید، محدودهٔ دسترسی نقش
و ذخیره‌سازی (حافظه در توسعه، Postgres در استقرار). صفحه‌های وب هم همین شناسهٔ ماژول را
از سرور می‌خوانند و جدول، فرم و دکمه‌های اقدام را خودکار می‌سازند
(`design/prototype/js/live_records.js`)؛ پس افزودن ماژول تازه یعنی نوشتن یک شناسهٔ کوتاه،
نه یک صفحهٔ دستی.

برش‌های عمودی اختصاصی (کارگزینی و قراردادها، افراد تحت تکفل و پرواز، احکام حقوق و
گواهی اشتغال) جداگانه و با قواعد خودشان کار می‌کنند و چاپ سند (قرارداد قانون کار، حکم
حقوق، فیش حقوقی، گواهی اشتغال) با قالب راست‌چین و شیوه‌نامهٔ A4 از مسیر
`/api/v1/documents/{kind}/{id}` انجام می‌گیرد؛ پیش‌نمایش قالب با دادهٔ نمونه از
`/api/v1/documents/preview/{kind}` سرو می‌شود و `/api/v1/contracts/templates` قالب‌های
متن قرارداد را برمی‌گرداند. **هیچ مسیر `501` باقی نمانده است.**

**پارامتریک بودن کامل:** برند شرکت (**آرم رسمی هلدینگ خلیج فارس** و کد `BIPC`؛ آرم،
نام و رنگ برند از `logoFile`/`brandColor` در پروفایل شرکت خوانده می‌شود و در صفحهٔ ورود،
سرصفحه، نوار کناری، نشان نوار مرورگر، سرصفحهٔ اسناد چاپی و سرصفحهٔ گزارش‌ها می‌نشیند)،
سیستم حقوق و دستمزد (پارامترها و ضرائب + اقلام حقوق با فرمول/درصد/مبلغ از طریق
`/api/v1/payroll/parameters` و `/api/v1/payroll/simulate`)، متن قرارداد/فیش حقوق/احکام
(قالب‌های طراحی‌شدنی در `/api/v1/settings/records?kind=docTemplates`) و گزارش‌ساز بر
پایهٔ اقلام انتخابی (`/api/v1/reports/sources` و `/api/v1/reports/run` که سرصفحهٔ برند
شرکت را هم در پاسخ `brand` برمی‌گرداند) همه بدون تغییر کد و از راه داده تنظیم می‌شوند.

منبع حقیقت قواعد و گام‌های بعدی در `docs/operations-plan-fa.md` آمده است.

**برنامهٔ عملیاتی پنج‌گامی و فهرست نیازمندی‌ها** برای رساندن سامانه به محیط واقعی در
`docs/operations-plan-fa.md` است: از کدام ماژول شروع کنیم، هر گام چه چیزی را به چه
داده یا سندی از شما وصل می‌کند و معیار پذیرش هر گام چیست.

**راهنمای فنی استقرار، بهره‌برداری و پشتیبان‌گیری** (نیازمندی‌ها، سرویس دائمی،
Postgres و مهاجرت‌ها، پایش آمادگی و پاسخ به «کپی پوشه برای بک‌آپ کافی است؟») در
`docs/deployment-runbook-fa.md` است.

**اجرای محلی با دادهٔ واقعی** (راه‌اندازی وب‌سرویس روی همین رایانه با پایگاه‌دادهٔ
واقعی Postgres، بدون Docker: نصب، پیکربندی، دستورهای شروع/توقف و آن‌چه آزموده شد) در
`docs/hrms-local-postgres-fa.md` است. ساده‌ترین راه، دوبار کلیک روی `start-HRMS.bat`
است: کلاستر محلی Postgres را بالا می‌آورد، `server\bin\hrmsd.exe` را روی
`http://127.0.0.1:8080` اجرا می‌کند و رابط وب را — که همان API واقعی را می‌خواند —
در مرورگر باز می‌کند.

**«سیستم پاداش»** برای واحدی که فقط کار پاداش را انجام می‌دهد و می‌خواهد روی یک
رایانه و بدون پایگاه‌داده و بدون Docker کار کند: یک فایل اجرایی با رابط وب جاسازی‌شده و
یک پوشهٔ دادهٔ خودکفا (`make bonusd` سپس `make run-bonusd`). برای ویندوز ۳۲بیتی هم
`make bonusd-386` ساخته می‌شود. رمز پیش‌فرض مدیر `admin`/`6468` است؛ سرصفحهٔ رابط
آرم سازمان (جاسازی‌شده در باینری) و خط «مالکیت برنامه: مسعود وائقی» را دارد و دکمهٔ
«🖨 چاپ گزارش» یک گزارش A4 فارسی تولید می‌کند. پلن ساخت،
مراحل اجرا، پشتیبان‌گیری و محدودیت‌های آگاهانه در `docs/bonus-standalone-fa.md` است.

همین سامانه یک **نسخهٔ دسکتاپ ویندوزی** هم دارد: پنجرهٔ بومی WebView2 با آیکون مستقل در
نوار وظیفه، بدون کنسول و بدون نوار نشانی مرورگر، با دو دکمهٔ بومی «پوشهٔ داده» و
«ساخت پشتیبان» (`make bonusapp` سپس `make run-bonusapp`). همان رابط HTML و همان API؛
هیچ صفحه‌ای بازنویسی نشده و بستهٔ پرتابل، بدون CGO و بدون DLL همراه ساخته می‌شود.
برای ویندوز ۳۲بیتی هم `make bonusapp-386` موجود است (نیازمند موتور WebView2 نسخهٔ x86).

**ویندوز ۷/۸/۸٫۱ پشتیبانی نمی‌شود.** Go از نسخهٔ ۱٫۲۱ به بعد فقط ویندوز ۱۰+ را
پشتیبانی می‌کند و WebView2 SDK جدید هم ویندوز ۸/۸٫۱ را نمی‌پذیرد؛ پس هر دو نسخه روی
این ویندوزها اجرا نمی‌شوند. راه‌حل: `bonusd.exe` را روی یک رایانهٔ ویندوز ۱۰/۱۱ با
`-addr 0.0.0.0:8099` اجرا کنید و از مرورگر رایانهٔ قدیمی به نشانی شبکهٔ چاپ‌شده در لاگ
وصل شوید (یا رایانه را به ویندوز ۱۰/۱۱ ارتقا دهید). جزئیات در
`docs/bonus-standalone-fa.md` بخش ۹.
